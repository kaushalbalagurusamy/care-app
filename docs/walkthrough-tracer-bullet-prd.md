# CARE first-user walkthrough fixes — tracer-bullet PRD

**Source:** first-user simulator walkthrough, 29 September 2026. **Status:** implemented; final simulator and CI evidence is recorded below. This document describes requested behavior; existing architecture notes are not evidence of implementation. Each item below maps to executable source and a failing-before-fix evaluation.

## Product rules and boundaries

- **No age field** exists for the account holder, contacts, or historical person snapshots in live forms, domain models, result presentation, search, sort, or new persistence. Upgrade must retain names, relationships, photos, answers, scores and history from stores created by the prior model. The survey's guidance about excluding minor children is advice, not an age field or an app-enforced age check.
- **Relationship to you** is optional free text. Name alone is required. A legacy saved category, including “Other Relative,” remains readable and displays “Other” where relevant; newly entered contacts are never forced into a category.
- An assessment requires **at least five saved contacts and exactly five selected contacts**. The selection count is explicit and the forward action remains disabled until the count is five.
- A **flow** is an assessment, exercise, or education quiz. Back before the final action moves to the preceding step in that flow and restores editable input, even after leaving, saving and resuming. A final Submit/Complete ends the flow; Back from results/completion never reopens its editor.
- **One completed assessment per local calendar day** is allowed. An unfinished assessment can resume on a day with no completed assessment. The entry screen and the atomic result commit both enforce the rule. Existing same-day historical duplicates remain readable and individually addressable by result ID.
- Every saved assessment is addressable from its trend point by stable result ID. **Do not silently prune the 51st or later assessment** while this history promise is in force. A separate, explicit retention policy can be designed later.
- “Highest rated” orders by persisted star rating; Favorites filters by persisted favorite flag. “Most used” and number of times completed use persisted completion count; Recent uses latest completion date. Duration uses numeric lower and upper minute bounds, while display can retain the range string.
- The weekly **x/7** value counts distinct local days with at least one completed exercise. Category counts and streaks use that category's completions; the all-exercises weekly display deduplicates dates across categories. Completing seven exercises on one day yields **1/7**, not 7/7.

## Required test and CI changes

1. Add the tests above to the existing `CAREAppTests` / `CAREAppUITests` targets. New files must be registered in `CAREApp.xcodeproj`; tests must assert observable behavior and persisted records, not only that a view initializes.
2. Add a macOS iOS-test job to `.github/workflows/ci.yml` for pushes and pull requests. Select an available iPhone simulator at runtime, run `xcodebuild test` for scheme `CAREApp` with signing disabled, and upload the `.xcresult` bundle on failure. Keep backend pytest as a separate required job.
3. CI's iOS job must run migration/reopen, scoring/day-limit, sorting/streak, flow-state and UI-route tests. A green simulator build alone is insufficient.
4. On the dedicated clean simulator, manually replay: profile setup → add five contacts → select five → assessment → save/leave/resume/back/edit → submit → historical point; then exercise and quiz save/resume/back/complete. Confirm no sample data appears. Preserve this simulator's data between checkpoints for persistence checks.
5. Run the full iOS suite locally and in CI, inspect `.xcresult` failures, compare critical screen captures, and request an independent source review of the mechanism. A passing test that bypasses the real route/store is not acceptance.

## Baseline source observations before this implementation

- `Theme.Typography.body` is Poppins regular 15; `subheadline` is medium 14; the Survey Instructions subtitle currently hard-codes regular 13. There is no dedicated screen-subtitle token yet.
- `AppRouter` currently tracks visited screens. It does not know a flow's prior step, so resume-from-Home then Back can leave the flow.
- `QuizDraft` currently has a cursor/current selection/aggregate score, but not a complete answer history for correction.
- Exercise duration is currently a display string, and the current duration sorter takes its final number for both shortest and longest.
- The current CI workflow runs backend pytest only. The iOS simulator suite passed 167/167 during the preceding data-hardening run, but is not yet a CI gate.

The CI workflow now runs the full iOS unit and UI suite on an available iPhone simulator and uploads its result bundle, alongside the existing backend job. The final local combined run on an **iPhone 16e, iOS 18.6** passed **190/190 tests: 181 unit tests and nine UI journeys**, with no failures or skips. The verified result bundle is `/private/tmp/care-walkthrough-all-final.xcresult`.

An independent source review found and prompted fixes for chart hit-target overlap, the alternate assessment writer's missing day check, the person-transition Back boundary, quiz completion warnings, and selected-option contrast. It initially flagged exercise Back as warning before step navigation; source inspection showed that Back directly invokes each exercise's own step handler and the generic warning applies to other header destinations.

**Release checks still requiring a human:** inspect large Dynamic Type presentation and the actual YouTube player's settings/close interaction on a device with network access. The simulator UI check verifies the top-left close target and description geometry. GitHub-hosted CI will first execute after the branch is pushed or a pull request is opened. Test fixtures activate only with explicit `--uitesting-*` launch arguments and use an in-memory store; normal launches continue to use the user's persistent data.
